# Corrélateur FB — diagnostic du READ path (I/Q)

## Read path

END-TO-END. WRITE side (input I/Q): the BSP writes the live decimated I/Q into DSP DARAM at word 0x2a00, span [0x2a00..0x2b28) = 296 int16 = 148 interleaved I/Q pairs. Cites: calypso_bsp.c:97/169/496 `int16_t iq[296]` (148 pairs), calypso_bsp.c:109/193 `daram_addr` default 0x2a00 (the 2026-05-28 canary fix that moved the old 0x3FB0 default), and the actual store loops calypso_bsp.c:1111-1119 (DIRECT_FEED rx_burst) and 1324-1336 (deliver_buffered), both storing `dsp->data[(uint16_t)(daram_addr+woff)] = iq[i]`. Canary proof the DSP reads 0x2a00 lives at calypso_bsp.c:776-784 (PC=0x93a5, AR3=0x2a00 read back 0xCAFE). READ side (correlator): the FB-det handler entry is 0x8d00; the genuine FB MAC that consumes I/Q is at PC=0xee38 and dereferences the input via AR3 post-increment. On the native path AR3 must be based at the buffer start 0x2a00 and swept across the 148-pair window (IQ-READ tracer watches exactly [0x2a00..0x2b28), calypso_c54x.c:1596-1628; SPAN-READ dumps data[0x2a00..0x2a1f] at :1627). In THIS run AR3 at 0xee38 instead points at 0x2b97, inside region [0x2b80..0x2c00) which is disjoint from and 0x58 words ABOVE the written buffer end 0x2b28 — cited verbatim at calypso_c54x.c:7209-7215 ("le dispatch avance bien à PC=0xee38 ... mais AR3 y pointe HORS du buffer I/Q (0x2b97 > 0x2b28) → corrèle des zéros ... le setup d'AR3/pointeurs en amont de 0xee38 est aussi mal émulé"). So: BSP writes at 0x2a00; correlator reads via AR3 at 0x2b97 / via AR5 at the staged immediate 0xdb7b — never at 0x2a00.

## Pourquoi il lit constant (le mismatch)

The correlator reads CONSTANT data because it was entered via a FORCED dispatch straight to the FB-det body 0x8d00, which BYPASSED the native per-task LUT dispatcher at 0x8341 that is the only thing that programs the correlator's data pointers (AR3/AR5), BK (circular length) and BRC. 0x8341 computes the task handler target from the LUT slot data[(DP<<7)|0x07] and, for task_md=5, installs the pointer table basing AR3/AR5 at the I/Q buffer 0x2a00 with BK = buffer span (dispatcher entry/LUT logic: calypso_c54x.c:3924-3980, and the DP→0x8341→CALAD chain at :5810, :11794, :13372). Because 0x8341 was skipped, those pointers were never initialized to 0x2a00. AR5 is therefore left/clobbered to a hard staged immediate 0xdb7b — laundered ST #0xdb7b→dma0x60 @0x8e80, LD dma0x60→A @0x8e88, STLM A,AR5 @0x8e89 — and the 0x8e8b/0x8e8c body is an MVDD block-copy (op 0xe5ba = *AR4+ = *AR5+, calypso_c54x.c E5xx handler ~7755-7787), NOT a MAC. AR5=0xdb7b and dest AR4=0x2bc0 stay PINNED, so it copies the same 2 words (val 0x001a→0x2bc0, 0x900c→0x2bc1) tens of thousands of times (pc[0x8e8c] 7995→815452 over the run, pure spin). And AR3 at the real MAC 0xee38 sits at 0x2b97, above the 0x2b28 buffer end, so even past the copy it MACs a stale/zero window. Net: read pointer never lands on the live samples at 0x2a00 → constant input → constant coeffs → no peak → d_fb_det never set. (Runtime corroboration: 0x2a00 has ZERO data-access hits in the 389k-line log and, per the note, was not even written this run — a second, independent starvation on top of the pointer bug.)

## Le fix (2 couplés)

Two coupled fixes, both required. (1) STOP forcing entry at 0x8d00 and route the scheduler natively: wire 0x013b → 0x8341 so the prologue (chain 0xf0→0x7234→0x013b→0xa4e4, calypso_c54x.c:12341-12345) actually reaches the LUT dispatcher at 0x8341. That runs the native FB-det setup for task_md=5, which loads the correct LUT slot and installs the pointer table so AR3 (and AR5) are based at the BSP I/Q buffer 0x2a00 and BK/BRC are set to the 148-pair span — instead of the garbage AR5=0xdb7b / AR3=0x2b97 the forced-dispatch shortcut leaves behind. Concretely: remove/bypass the CORR force-to-0x8d00 shortcut so 0x013b falls through 0xa4e4→…→0x8341, letting the native dispatcher program BRC/BK/AR3/AR5 before the correlate phase. (2) Guarantee the buffer is actually populated: set CALYPSO_BSP_DIRECT_FEED=1 so calypso_bsp_rx_burst writes DARAM 0x2a00 every frame (calypso_bsp.c:1111-1119) rather than the FN-gated deliver_buffered path that never matches under icount=auto and leaves 0x2a00 empty. After (1)+(2) the native setup points AR3 at 0x2a00 AND real samples are present there, so the MAC input varies and a correlation peak is found. (If the native 0x8341 pointer table encodes a different base than 0x2a00, align CALYPSO_BSP_DARAM_ADDR to whatever base the LUT programs — but the canary at 0x2a00/PC=0x93a5 shows 0x2a00 is the native base.)
